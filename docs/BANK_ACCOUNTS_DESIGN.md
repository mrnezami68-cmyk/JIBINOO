# 🏦 طراحی فاز حساب‌های بانکی (فاز ۱۵+) — مشاوره معماری و نقشه راه

این سند تحلیل زیرساخت موجود، معماری پیشنهادی، ریسک‌ها و نقشه اجرای قابلیت
«چند حساب بانکی + انتقال بین حساب‌ها» را شرح می‌دهد. **هنوز کدی نوشته نشده است** —
این سند مبنای تصمیم‌گیری است.

---

## ۱. مسئله از زبان کاربر

کاربر ۴ حساب/کارت دارد:

| حساب | موجودی |
|---|---|
| بانک سامان | ۲۰٬۰۰۰٬۰۰۰ تومان |
| بانک سپه | ۱۰٬۰۰۰٬۰۰۰ تومان |
| بانک رسالت | ۸٬۰۰۰٬۰۰۰ تومان |
| بانک خاورمیانه | ۸٬۵۰۰٬۰۰۰ تومان |
| **مجموع نقد** | **۴۶٬۵۰۰٬۰۰۰ تومان** |

خواسته‌ها:

1. **مجموع نقد** در داشبورد مثل امروز نمایش داده شود (۴۶.۵ میلیون).
2. هر جابه‌جایی (هزینه، قسط، خرید دارایی، واریز حقوق، فروش دارایی) کاربر **حساب مبدأ/مقصد را انتخاب کند**.
3. **انتقال بین حساب‌ها** در دفتر ثبت شود، ولی نه درآمد/هزینه باشد و نه ارزش خالص را عوض کند.
4. هدف واقعی: **مدیریت پاکتی (Envelope)** — «این کارت برای خرج خانه است، آن یکی پس‌انداز، دیگری حقوق» ⇒ باید بتوانیم بگوییم «در کدام حساب چقدر خرج کرده‌ایم».

## ۲. ارزیابی زیرساخت موجود

### ۲.۱ نقاط قوت (چرا این فاز روی این کدبیس به‌خوبی می‌نشیند)

| # | نقطه قوت | رفرنس |
|---|---|---|
| ۱ | **تنها یک نقطه حقیقت برای اثر نقدی:** تابع `cashDelta(tx)` — هم ثبت هم حذف از همین استفاده می‌کنند (آینه دقیق). الگوی آماده برای `accountDelta(tx, accountId)` | `lib/store.tsx` |
| ۲ | **همه جابه‌جایی‌ها اتمیک‌اند:** هر اکشن = جهش موجودی + سند دفتر با `link` + جهش رکورد، در یک `setState`. `accountId` به‌طور طبیعی در همین کانال جاری می‌شود | `payLoan`, `transferGoal`, `addAsset`, `sellAsset`, `addLoan` |
| ۳ | **نقطه مهاجرت مرکزی:** `sanitizeState` از قبل داده ناقص را با پیش‌فرض‌ها ترمیم می‌کند — دقیقاً جایی که مهاجرت v2→v3 اضافه می‌شود | `lib/store.tsx` |
| ۴ | **پشتیبان‌گیری سازگار به‌بالا:** `importBackup` از همان `sanitizeState` استفاده می‌کند ⇒ فایل‌های پشتیبان قدیمی خودکار مهاجرت می‌کنند | `lib/store.tsx` |
| ۵ | **`cash` در API عمومی store جدا از ذخیره‌سازی است:** می‌توان ذخیره‌سازی را به `accounts[]` برد و `cash` را **مشتق** (Σ موجودی‌ها) بیرون داد — **بدون لمس کردن** داشبورد، هدر Layout و تحلیل‌ها | `StoreValue.cash` |
| ۶ | **`summarize` فقط تایپ‌های مشخص را می‌شمارد:** اضافه‌شدن تایپ جدید `transfer` به‌صورت ذاتی از درآمد/هزینه/سایر خارج است ⇒ **ریسک دوباره‌شمارشی صفر** | `lib/analysis.ts` |
| ۷ | **نقطه اعتبارسنجی مبلغ واحد است:** `value > cash` در TxModal — تبدیل به چک «مبلغ > موجودی *حساب انتخابی*» | `components/TxModal.tsx` |
| ۸ | **۴۱ تست رگرسیون** هر ۸ باگ یکپارچگی مالی را قفل کرده‌اند — همان تست‌ها برای حساب‌ها توسعه می‌یابند و رانش (drift) را می‌گیرند | `lib/__tests__/store.test.tsx` |

### ۲.۲ نقاط ضعف / چالش‌های فاز ۱۵

| # | چالش | شدت |
|---|---|---|
| ۱ | **`cash` به‌صورت شمارنده مستقل ذخیره می‌شود** (نه مشتق از دفتر). با آمدن حساب‌ها، نگه‌داشتن **دو** شمارنده (cash + Σaccounts) = ناورداینتِ تهدیدشونده. باید یکی حذف شود، نه اینکه هر دو نگه داشته شوند | بالا (معماری) |
| ۲ | **`Tx` فیلد `accountId` ندارد** ⇒ تراکنش‌های قدیمی در گزارش هر-حساب «بی‌صاحب»‌اند؛ سیاست fallback لازم است | متوسط |
| ۳ | **ورودی‌ها هم نیازمند انتخاب حساب‌اند** نه فقط خروجی‌ها: فروش دارایی، دریافت اصل وام، حقوق — طبق مثال خود کاربر «حقوق وارد فلان کارت می‌شود» | متوسط (طراحی UX) |
| ۴ | **حذف حساب با موجودی/تاریخچه** — سیاست لازم است (بلاک؟ انتقال+حذف؟ آرشیو؟) | متوسط |
| ۵ | **اصطکاک UX:** اگر هر ثبت هزینه سریع یک انتخاب الزامی اضافه شود، تجربه خراب می‌شود ⇒ مفهوم «حساب پیش‌فرض/آخرین استفاده» | بالا (تجربه) |
| ۶ | ~۱۰ نقطه تماس UI باید سلکتور حساب بگیرند (TxModal، دارایی خرید/فروش، وام ثبت/قسط، هدف واریز/برداشت، آنبوردینگ، فیلتر تراکنش‌ها) — دامنه قابل‌مدیریت ولی باید همه‌ی آنها پوشش داده شود وگرنه رانش | متوسط |

## ۳. معماری پیشنهادی

### ۳.۱ مدل داده (AppState v3)

```ts
export interface Account {
  id: string;
  name: string;            // «سامان خانه»، «سپه پس‌انداز»، «پول نقد»
  bank?: string;           // نام بانک (اختیاری — حساب می‌تواند کیف پول نقد هم باشد)
  icon?: string;           // ایموجی/آیکن انتخابی
  color?: string;          // رنگ کارت حساب
  balance: number;         // شمارنده — دقیقاً مثل cash امروز، فقط به‌ازای هر حساب
  isDefault?: boolean;     // پیش‌انتخاب در مودال‌ها (کاهش اصطکاک)
  archived?: boolean;      // حذف نرم — تاریخچه حفظ می‌شود
  note?: string;           // «فقط برای خرج خانه»
  createdAt: string;
}

// AppState:
//   accounts: Account[]    ← جدید
//   cash: number           ← از ذخیره‌سازی حذف؛ در StoreValue به‌صورت مشتق باقی می‌ماند:
//                          //   cash = accounts.reduce((s,a)=> s + a.balance, 0)
```

**تصمیم کلیدی ۱ — نقد مشتق، نه دوتایی:** شمارنده cash حذف و به‌صورت مشتق ارائه می‌شود.
ناورداینتِ «Σ موجودی‌ها = نقد کل» دیگر *قابل شکستن نیست* چون فقط یک منبع حقیقت وجود دارد.
Dashboard/Layout/analysis چون از `useStore().cash` مصرف می‌کنند، **بدون یک خط تغییر** کار می‌کنند.

```ts
// Tx گسترش می‌یابد:
interface Tx {
  /* …فیلدهای فعلی… */
  accountId?: string;      // حساب مبدا (برداشت) یا مقصد (واریز) — تراکنش‌های قدیمی: undefined
}

// تایپ جدید تراکنش:
TxType: 'income'|'expense'|'investment'|'goal'|'loan'|'transfer'

// انتقال بین حساب‌ها = یک سند واحد:
{ type:'transfer', kind:'transfer', accountId: fromId,
  link: { type:'account-transfer', toId }, amount }
```

### ۳.۲ موتور اثر — توسعه الگوی cashDelta

```ts
function cashDelta(tx)            // اثر روی نقد کل — برای 'transfer' صفر
function accountDelta(tx, accId)  // اثر روی یک حساب مشخص:
  // tx.type==='transfer':  → -amount اگر accountId==accId، +amount اگر link.toId==accId
  // غیر آن:                → cashDelta(tx) اگر tx.accountId==accId وگرنه ۰
```

همان قانون «ثبت و حذف از یک تابع» ⇒ برگشت انتقال (حذف سند) به‌صورت اتمیک هر دو حساب را برمی‌گرداند.

### ۳.۳ جریان هر اکشن (تغییرات فاز ۱۵)

| اکشن موجود | تغییر |
|---|---|
| `addTx` | پارامتر `accountId` (الزامی برای تایپ‌های جدید؛ برای واریز/برداشت) |
| `payLoan` | `+ accountId` (کسر قسط از کدام حساب) |
| `addLoan(receiveCash)` | `+ accountId` (اصل وام به کدام حساب واریز شود) |
| `addAsset(fromCash)` | `+ accountId` (هزینه خرید از کدام حساب) |
| `sellAsset` | `+ accountId` (حاصل فروش به کدام حساب نشیند) |
| `transferGoal` | `+ accountId` (واریز/برداشت هدف با کدام حساب) |
| `setCash` (آنبوردینگ) | به `addAccount({name:'پول نقد', balance})` تبدیل می‌شود — موجودی اولیه، موجودی اولین حساب است |
| **`transferBetweenAccounts(fromId, toId, amount, date)`** (جدید) | سند واحد `transfer` + جهش دو شمارنده، اتمیک |

`deleteTx` به‌طور خودکار از همان `accountDelta` استفاده می‌کند ⇒ حذف هر سند، اثرش را دقیقاً از همان حساب برمی‌گرداند (تعمیم باگ ۷ به حساب‌ها).

### ۳.۴ مهاجرت v2 → v3 (در `sanitizeState`)

```
اگر accounts وجود ندارد یا خالی است:
  حساب پیش‌فرض بساز: { name:'پول نقد', balance: legacyCash, isDefault:true }
فیلد cash قدیمی نادیده گرفته می‌شود (پس از انتقال به حساب).
```

⇒ کاربر فعلی با ۱ نفرِ تاریخچه، روز بعد فقط یک حساب «پول نقد» می‌بیند و هیچ عددی نمی‌پرد.
⇒ فایل پشتیبان v2 هم از این قیف رد می‌شود ⇒ سازگاری کامل نسخه‌ها.

### ۳.۵ UI — چه چیزی کجا

| صفحه/کامپوننت | تغییر |
|---|---|
| **صفحه جدید «حساب‌ها»** | کارت هر حساب: موجودی، ورودی/خروجی ماه جاری، دکمه ویرایش/آرشیو، دکمه «انتقال بین حساب‌ها»، افزودن حساب |
| داشبورد | نقد کل (مشتق) مثل امروز + ردیف چیپ‌های کوچک موجودی هر حساب |
| TxModal | چیپ‌سلکتور «از/به حساب» (پیش‌انتخاب: حساب پیش‌فرض یا آخرین استفاده) + خطای «موجودی *این حساب* کافی نیست» با پیشنهاد انتقال |
| دارایی‌ها (خرید/فروش)، وام‌ها (ثبت/قسط)، اهداف (واریز/برداشت) | همان سلکتور مشترک (کامپوننت واحد `AccountPicker`) |
| تراکنش‌ها | نمایش نام حساب روی هر سند + فیلتر بر اساس حساب؛ اسناد قدیمی در سطل «بدون حساب (قدیمی)» |
| آنبوردینگ | مرحله اختیاری: لیست حساب‌ها با موجودی (یا یک مبلغ تکی ⇒ یک حساب پیش‌فرض) |

## ۴. ریسک‌ها و راهکارها

| # | ریسک | راهکار |
|---|---|---|
| ۱ | **رانش شمارنده‌ها** (موجودی حساب با واقعیت نخواند) | یک `accountDelta` واحد برای همه جهش‌ها + تست ناورداینت «Σ حساب‌ها = cash مشتق» + تست رگرسیون برگشت انتقال در `store.test.tsx` |
| ۲ | **خطای اعتبارسنجی اشتباه** (چک روی نقد کل به‌جای حساب) | همه چک‌های `value > cash` به «موجودی حساب انتخاب‌شده» تبدیل شود؛ پیام خطا موجودی همان حساب + راهنمای انتقال را نشان دهد |
| ۳ | **حذف حساب دارای موجودی** | بلاک با پیام + گزینه «انتقال موجودی و حذف» (تراکنش انتقال ثبت شود بعد حذف) |
| ۴ | **حذف حساب دارای تاریخچه** ⇒ اسناد یتیم | «آرشیو» به‌جای حذف: از سلکتورها پنهان، در تاریخچه حاضر. حذف فیزیکی فقط وقتی هیچ سندی به آن اشاره نکند |
| ۵ | **تراکنش‌های قدیمی بدون accountId** | تعریف‌شده: مساوی «حساب پیش‌فرضِ زمان مهاجرت» برای نمایش، و در فیلتر تحت «قدیمی». موجودی‌ها به‌خاطر مهاجرت شمارنده‌ای درست‌اند |
| ۶ | **اصطکاک ثبت سریع** | `isDefault` + به‌خاطر سپردن آخرین حساب استفاده‌شده (در settings) ⇒ ثبت سریع همچنان ۱-تپ |
| ۷ | **شکستن backup های قدیمی** | مهاجرت در sanitizeState ⇒ هر دو قالب خوانده می‌شوند؛ خروجی جدید با برچسب `version: 3` |
| ۸ | **تحلیل‌ها (سلامت مالی و…)** | همه به نقد *کل* نگاه می‌کنند ⇒ با cash مشتق بدون تغییر درست‌اند. تحلیل هر-حساب، افزونه فاز بعد است (فاز ۱۶) |
| ۹ | **مغایرت با بانک واقعی** (کاربر فراموش کرده چیزی ثبت کند) | فاز ۱۶: اکشن «تصحیح موجودی» که سند تعدیل ثبت می‌کند (نه ویرایش خام شمارنده) — راستی‌آزمایی باقی می‌ماند |

## ۶. سناریوی کاربر پس از فاز ۱۵ (با مثال خود کاربر)

1. کاربر ۴ حساب می‌سازد و موجودی فعلی هر کدام را می‌زند ⇒ داشبورد همان «۴۶/۵ میلیون» را نشان می‌دهد.
2. حقوق ۳۵ میلیون می‌آید ⇒ تراکنش درآمد به حساب «سامان (حقوق)».
3. ۱۵ میلیون را از سامان به «سپه (پس‌انداز)» منتقل می‌کند ⇒ سند انتقال ثبت می‌شود؛ نقد کل و ارزش خالص **هیچ** تغییری نمی‌کند.
4. ۲/۴ میلیون خرج خانه از کارت «رسالت» ⇒ فقط موجودی رسالت کم می‌شود.
5. قسط وام ۵ میلیون از «خاورمیانه» ⇒ در همان مودال قسط، حساب مبدأ انتخاب می‌شود.
6. ته ماه: گزارش هر-حساب می‌گوید «از رسالت ۲/۴ میلیون خرج خانه شده» — دقیقاً همان چیزی که کاربر می‌خواست.

## ۷. تصمیم‌های باز (نياز به تأیید کاربر)

1. **نقد مشتق** (پیشنهاد قوی: بله) — یا نگه‌داشتن دو شمارنده؟
2. **حساب پیش‌فرض + آخرین استفاده** برای جلوگیری از اصطکاک (پیشنهاد: بله)
3. **سیاست حذف:** بلاکِ حذف حسابِ دارای موجودی + آرشیو برای دارای تاریخچه (پیشنهاد: بله)
4. **«پول نقد» به‌عنوان حساب از نوع کیف پول** (پیشنهاد: بله — مهاجرت هم خودش یکی می‌سازد)
5. تقسیم اسکوپ: فاز ۱۵ (زیرساخت) جدا از فاز ۱۶ (تحلیل پاکتی)؟ یا یک PR بزرگ؟
